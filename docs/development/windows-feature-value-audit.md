# Windows 分支功能价值审查

审查日期：2026-09-28。目标是判断哪些增量值得合入、哪些应简化或删除，不以提交数量或测试数量代替用户价值。

## 范围与结论

- 比较基线：`origin/main`，`725aab0`。
- 被审查分支：`origin/codex/windows-platform`，`78514d9`。本轮已刷新远端引用。
- 辅助验证环境：`codex/platform-integration`，`324a137`，macOS 原生工具链。未改动主线、用户配置或现有应用。
- Windows 相对 main：180 个提交、124 个文件、增加 27,408 行、删除 1,975 行。其中 82 个提交以 `chore` 开头；新增文档 4,686 行，独立测试及评测工具 4,338 行，应用代码目录 18,314 行（还包含 Rust 内联测试），构建/工具配置 70 行。不能把这些数字理解为新增了 180 项功能。

结论：有值得保留的功能，也有尚未证明收益的增强、没有进入运行流程的预留接口，以及实际会损害输出的规则。不建议整块回退 Windows 分支，也不建议原样放行所有行为。应先修正会改变正常文本的规则和无效设置，再删无调用的接口，保留核心功能及其兼容路径。

`main` 已有多 ASR 提供商、AI 助手、自动词汇学习、TNL 文本归一化和 LLM 供应商管理。以下评估只给本次新增的部分记功。此前集成分支补的旧配置保护、Mac 适配和具体千问模型列表，不计为 Windows 原始实现的成果。

## 功能清单与处理意见

| 增量 | 用户能得到什么 | 价值及证据 | 处理意见 |
|---|---|---|---|
| 千问 Audio 3.0 / 3.1 协议与档位，保留 Qwen3 | 可用更多 ASR 模型 | 高；HTTP、流式请求和 UI 都有接入。Windows 原实现是三个档位，集成分支再扩展为具体模型选择 | 保留协议适配和模型选择；旧用户继续原模型，不能因缺新字段而换模型 |

| 热词统一去重、排序、数量限制、把纠错目标送入 ASR | 有限热词配额优先给用户自己的词，复用已学纠错 | 中高；Qwen/Doubao 的 HTTP 和流式均有调用 | 保留正在使用的 ASR 编译与渲染路径，删除没有消费者的 TNL/LLM pack 预留接口 |
| 词条分类、短语匹配、邮箱/URL/代码符号区别处理 | 少把链接、代码当成普通近音词改掉 | 中高；分类参与实际算法路由，并非仅多一列标签 | 保留元数据和保护规则；自动推断为主，减少要求用户手工分类的负担 |
| Jieba 分词及词性识别人名、地名、机构名，参与候选权重 | 尝试保护中文专名或优先匹配 | 有调用，不是死代码；但没有针对该增强的真实录音对照收益和成本数据 | 暂不扩展，补独立对照再决定长期保留；本轮不直接删除依赖 |
| 从最近 24 小时历史、当前应用文本提取临时热词 | 最近说过或屏幕正在编辑的技术词更容易识别 | 中等潜力；主要是 ASCII/技术词，不是普适中文上下文理解 | 建议实验性、可显式关闭；先量化识别收益及起录等待。保留手工词典作为稳定基础 |

| SQLite 用户词典、分类/来源/启用状态、与 JSON 保存解耦 | 独立管理词条，普通设置保存不覆盖词典 | 数据组织有价值；也增加迁移和双份数据维护成本 | 当前已是词典真实读写路径，不可直接删库或回退到旧快照；可以删未使用查询，保留读写与迁移 |
| LLM 思考模式、额外请求参数 | 调整延迟/回答深度，兼容供应商参数 | 思考控制值得保留，但目前统一七档并非七种有效行为 | 按模型能力展示选项；未知模型不冒充支持。额外参数留在高级配置，不强迫普通用户理解 |
| 评测器、消融、草稿导入、readiness、开发文档 | 支持开发者判断哪些纠错真的有效 | 有开发价值，无直接用户功能；本轮确实用其找出缺陷 | 保留离线评测和有用回归；压缩阶段性规划、重复文档；不再拿“小样本全过”代替真实验收 |
| 运行时自动保存纠错诊断原文 | 方便开发排错/采集评测草稿 | 常态使用的收益低，有额外文本落盘与文件扫描 | 改为主动开启的诊断模式，增加跨天保留期限/总量上限 |
| CMake 兼容处理、GitNexus/Trellis 清理 | 构建可用、减少开发流程负担 | 工程价值，不是用户功能 | 保留清理结果；Windows `.cmd` 的全局 CMake 绑定已在集成分支修正，不能恢复 |

## 本轮实证

### 1. 纠错有局部效果，但没有 main 对 Windows 的完整质量对照

在集成工作树执行：

```sh
cd src-tauri
cargo run --bin eval_asr --no-default-features -- --diagnostics-out /tmp/push-to-talk-windows-value-audit
target/debug/eval_asr --disable-syllable-match-pass --allow-quality-gate-failure --diagnostics-out /tmp/push-to-talk-windows-value-audit/without-syllable
cd ..
npx tsx scripts/asr-eval-readiness.ts --allow-not-ready --json
```

| 验证 | 结果 | 能证明什么 |
|---|---|---|
| 当前固定文本集 | 32/32；误替换 0；本次本地 p95 约 1.13ms | 对这些指定文本和纠错种子，算法能得到预期结果 |
| 禁用发音/别名匹配 | 22/32 | 在这批用例中，有 10 条依赖这一匹配路径 |
| 评测集规模检查 | 32/80，缺 48，`ready=false` | 连仓库自己的样本数量门槛都尚未达到 |

限制：`eval_asr.rs` 的 `evaluate_cases` 只调用口头语清理和本地个性化转换，不运行麦克风、云端 ASR、完整 TNL/Jieba 上下文流程、LLM、选区或粘贴。32 条数据是固定文本 fixture，种子与测试场景相关，不是独立真实录音盲测。消融也不是原 main 与 Windows 的完整 A/B，不能宣称“比 main 提升 31.25%”。80 条仅是仓库的数量门槛，达到也不自动代表统计充分。

`eval_asr.rs`、固定数据集、个性化 engine/ConvertPipeline、口头语清理代码均与 Windows 被审查提交相同；集成验证未把这几个模块改成另一套算法。但运行平台是 Mac，延迟不能外推到 Windows。

### 2. 口头语规则有可复现的语义损失

本轮在 `/tmp/push-to-talk-windows-value-audit/extra-guards` 建立空纠错表和四个人工反例，期望保持用户正常表达，使用同一评测器执行：

| 模式 | 输入 | 实际输出 | 问题 |
|---|---|---|---|
| 保守 | `这个，给小王；那个，给小李。` | `给小王；那个，给小李。` | 指代对象被删掉 |
| 保守 | `嗯。` | 空字符串 | 肯定回应被整个清空 |
| 激进 | `哈哈哈，太好笑了` | `哈，太好笑了` | 正常笑声被压缩 |
| 激进 | `好好好，就这么办` | `好，就这么办` | 语气表达被压缩 |

这是刻意挑选的边界反例，不是总体错误率。定位：`src-tauri/src/tnl/disfluency.rs` 的 `strip_leading_filler`、`remove_simple_false_start`、`collapse_repeated_cjk_chars`。当前基于文本和标点的规则不能区分停顿词与有效语义；“保守”也不能保证无损。

建议优先保证不会把非空回复清空，重新限定“这个/那个”等内容词的删除条件；在尚无语音停顿依据时，不将连续三个汉字一律压成一个。保留配置枚举的反序列化兼容，移除危险规则不等于删除旧配置字段。

### 3. 七档思考设置存在无效或重复选择

代码位置：`src/components/llm/ReasoningEffortSelect.tsx:11`、`src-tauri/src/llm_reasoning.rs:33`。

- UI 对所有模型统一显示默认、关闭、自动、低、中、高、极高。
- 被代码识别为 Qwen thinking 的模型：自动/低/中/高都只发 `enable_thinking=true`；“极高”分支未给它生成参数。
- 被代码识别为 OpenAI reasoning 的模型：“高”和“极高”都发 `reasoning_effort="high"`；“关闭”没有对应参数分支。
- 不匹配这些名称规则的模型，即使选择档位，也可能不发送任何思考参数。

这是本地请求构造逻辑的事实，不是对供应商当前协议的外部认证。修复时应逐模型/协议验证能力，只展示有效选择，不能静默让用户的选择失效。旧值继续可读；模型默认行为仍是兜底。

### 4. 确认没有生产调用的预留接口

全仓库引用检查发现，以下符号只有定义、包装函数或测试引用，没有接入应用运行流程：

| 位置 | 内容 | 建议 |
|---|---|---|
| `personalization/hotword_compiler.rs:41`、`:103` | `TnlDictionaryPack` 及 `compile_tnl_dictionary_pack*` | 可删该预留路径及专门测试，保留真正运行的 TNL 模块 |
| `personalization/hotword_compiler.rs:47`、`:131` | `LlmContextPack`、`CorrectionHint` 及 `compile_llm_context_pack*` | 可删预留路径；现有 LLM 提示词/仲裁没有依赖这些 pack |
| `personalization/hotword_compiler.rs:64` | `compile_user_dictionary_asr_pack` 简单包装 | 目前测试在用，可改为测试辅助或让测试直接调用生产入口；清理收益小 |
| `personalization/user_terms_store.rs:328`、`:344` | 两个 SQLite 发音键查询 API | 没有运行期消费者，可清理 API；数据库历史列先兼容保留，无须破坏性删列 |

不要把这份清单理解为可删除全部热词编译器、发音匹配算法或数据库。ASR 真正使用的是 `compile_asr_pack_with_correction_pairs`；个性化匹配使用纠错对索引；SQLite 的词条读取、写入、删除确实被前端命令调用。

ASR pack 内还有权重/别名元数据；当前两个通用 renderer 主要输出词文本，权重参与本地排序。不能宣传成所有供应商都收到了权重/别名控制，也不能因没在网络载荷出现就把排序权重删掉。

### 5. 运行诊断应从常态路径退出

`personalization/runtime_diagnostics.rs` 会保存 source/output、候选等字段；单字符串最多 160 字符、候选最多 20 条、每天最多 200 个文件。`prune_runtime_diagnostics` 仅扫描当日目录，没有跨日过期清理。

普通听写的 `pipeline/normal.rs:351` 和助手的 `lib.rs:608` 在获得个性化结果后直接尝试写文件，调用点没有独立的诊断开关。并非每次录音都写：纠错对文件不存在时会提前返回；一旦获得结果，即使没有改字也可写。

这是帮助开发者的能力，普通用户不需要常态积累这类原文副本。建议默认关闭、主动开启后限时/限量，写入失败仍不得阻断听写；开发评测器继续保留。不要通过删除用户已有诊断或历史来实施此改动。

### 6. 上下文热词值得试，但其适用范围和成本要说清

- `src/utils/recentHotwords.ts` 读取最近 24 小时成功历史，优先润色后文本，最多生成 20 条；提取规则以英文、大小写、代码符号为主。“处理成功”不等于“用户确认正确”，因此有把旧错误再次强化的可能。
- `personalization/app_context_hotwords.rs` 最多分析前 4,000 字符、提取 20 条，排除部分链接/邮箱，主要识别 ASCII 技术词。
- `lib.rs` 起录准备流程会等待原生文本读取再构造 ASR 客户端。这是实际增加的等待步骤；本轮没有测量 Windows 起录延迟，也没有声称已复现快速松键故障。

建议把这一增强作为清晰可控的实验项，补“开启/关闭”真实录音对照以及起录延迟测量。集成分支已保护旧配置不自动开启，但尚不能因此宣称新用户的默认体验已充分验证。

## 清理顺序

1. **优先修正用户能感知的错误。** 收紧口头语清理；思考模式按能力展示；运行诊断改成主动开启。用上面的反例先建回归，再改实现。
2. **删除无生产调用的预留代码。** 删除 TNL/LLM pack、未使用数据库查询；同步专门文档/测试。保留 ASR 热词编译、词典数据库、旧配置读取。
3. **控制实验功能边界。** 上下文热词、复杂候选加权、Jieba 增强分别提供对照证据；不足时默认保守，不继续叠更复杂模型。当前仅两个固定 pass 的 `ConvertPipeline` 可以日后简化，但这不是优先问题，也不值得为减少几层抽象重写已有效的算法。
4. **维持助手扩展为可选。** 搜索、模式独立模型有真实用途，保留已配置用户的选择，避免它们成为纯听写用户的必配项。即使决定下架，也应先保留旧配置可读、提示停用，不能导致启动失败或丢失凭据。
5. **收拢开发资料。** 保留单一现行架构/接口文档与可运行评测；历史阶段路线图移入归档，避免重复维护。GitNexus/Trellis 已删，不恢复。

以上为清理前的审查快照，代码位置与 32 条评测结果对应当时版本。用户批准后已按顺序实施清理，现行行为与验收结果见 [清理验收记录](windows-feature-cleanup.md)。本报告没有证明所有新增功能都有收益；Windows 覆盖升级和真实语音对照仍需独立验收。
