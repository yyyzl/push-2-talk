# 恢复 AI 助手选区上下文推理

## 目标

恢复 AI 助手在“用户先选中文本，再按助手热键提问/下指令”时的上下文感知体验：选中文本必须成为本轮模型思考的主上下文，用户的语音或文本追问应基于这段文本被理解，而不是退化成普通问答、机械文本改写，或被旧会话模式弱化。

## 已知事实

- 用户确认期望行为是：有选中文本时，AI 助手应基于这段文本再理解用户要问/要处理的问题。
- 当前后端仍会捕获选中文本，并通过 `selected_text` 进入 `AssistantProcessor::process_turn`。
- 结果面板/多轮对话改造后，`ConversationSession.system_prompt_mode` 是首轮锁定的。
- 面板打开期间再次按 AI 助手热键会进入追问路径，而不是天然创建新会话。
- 文本追问 `send_text_question` 当前永远传 `selected_text: None`。
- 默认“文本处理模式”提示词更偏向“直接输出处理后的结果”，对“基于选区回答问题/解释/分析”的约束不够友好。

## 需求

- 有选中文本的任意一轮，都必须把选中文本作为本轮用户消息的显式上下文。
- 当本轮有选中文本时，模型应优先围绕本轮选区作答；历史对话只能作为辅助上下文。
- 文本处理提示词要支持“处理文本”和“基于文本问答/解释/分析”两类意图，而不是一律只输出改写结果。
- 结果面板中每一次 AI 助手询问卡都要展示本轮选中文本，让用户能确认本轮问题基于哪段原文。
- 选中文本展示应适合长文本：默认显示摘要，不能撑爆用户气泡；需要保留查看完整原文的入口。
- 不破坏现有结果面板、多轮追问、联网搜索、流式输出和取消逻辑。
- 不重新引入长时间持有 `ClipboardGuard` 的旧问题。

## 验收标准

- [ ] 首轮有选中文本时，构造给 LLM 的 user message 包含选中文本和用户指令。
- [ ] 已有会话中再次选中新文本并用语音追问时，新选区在本轮消息中明确标记为“本轮选中文本/主要上下文”。
- [ ] 结果面板的每个用户询问卡片在 `has_selection=true` 且有 `selected_text` 时展示选中文本摘要。
- [ ] 结果面板 pending 卡片也展示本轮选中文本，不只在完成后展示。
- [ ] 长选中文本不会导致结果面板横向溢出或卡片高度失控。
- [ ] 文本处理默认提示词明确支持“基于选区回答问题、解释、分析、提建议”和“编辑/翻译/润色/总结”。
- [ ] 旧的文本处理命令（润色、翻译、总结、改写）仍然只输出处理结果。
- [ ] 相关 Rust 单元测试覆盖消息构造和默认提示词意图。
- [ ] 至少运行相关后端单元测试和 `cargo check`。

## 技术方案候选

### 方案 A：最小修复，增强 Prompt 与消息标记（推荐）

- 调整 `format_user_content` 的选区消息格式，把选中文本标记为“本轮选中文本/主要上下文”。
- 更新后端和前端默认 `text_processing_system_prompt`，让它成为“选区上下文助手”：先判断用户意图，处理类任务直接输出结果，问答/解释/分析类任务给出回答。
- 调整 `ResultPanelWindow` 的用户气泡：有选中文本时在询问文本下方展示“选中文本”摘要，并支持展开/收起查看完整内容。
- 保持 `process_turn` 签名和 `PromptMode` 存储结构不变，降低对联网搜索/流式输出的影响。

优点：影响面小，能直接修复“有选区但模型思考不像基于选区”的主要体验问题。
缺点：已有用户本地自定义提示词不会自动被覆盖，需要考虑是否做温和迁移或提示。

### 方案 B：按轮次动态选择 PromptMode

- 在追问路径中，如果本轮有新选区，使用 TextProcessing/Context 模式；如果无选区则可沿用会话模式。
- 可能需要把 `system_prompt_mode` 从“会话级”改成“轮次级/解析级”。

优点：语义更准确。
缺点：`process_turn` 影响分析为 HIGH，容易牵动语音追问、文本追问、联网搜索、历史工具上下文。

### 方案 C：有新选区时自动开启新会话

- 面板打开期间，如果用户在外部应用选中了新文本并按助手热键，默认关闭/归档旧会话并开启新会话。

优点：最接近旧的单轮助手体验。
缺点：会破坏当前“选中新文本作为追问材料”的能力，也可能让用户丢失多轮上下文。

## 推荐方向

先做方案 A。它最符合“恢复选区上下文推理”的核心诉求，同时避开 `process_turn` 的高风险签名/流程改造。后续如果用户明确希望“有新选区就自动新会话”，再单独做方案 C 的交互开关。

## 风险与约束

- `process_turn` 的上游影响为 HIGH：直接影响 `handle_assistant_mode`、`run_text_question_task`、联网搜索和流式输出。实现时应尽量不改签名。
- `ClipboardGuard` 必须在捕获后立即释放，不能为了恢复旧体验而重新持有到 LLM 完成。
- 当前前后端各有一份默认提示词，需要同步修改，避免新安装/旧配置补齐行为不一致。
- 如果用户本地已有旧提示词，默认常量修改不会自动生效；是否做迁移需要谨慎，避免覆盖用户自定义 prompt。
